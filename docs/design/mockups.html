Tokens in play

  • Colors: surface.base, surface.raised-1 (rows, app bar), surface.raised-3 (active row fill — this is exactly D1's documented use for raised-3: "pressed/active fill on a raised-1 element"), accent.primary (selection ring + index badge fill), status.connected (app-bar chip).

Touch targets

  • Each preset row: touch.target.min = 64dp tall (measured, including the active row) — a preset switch is the single most performance-critical action in the app. Pass.

  • Settings gear (top-right): touch.target.secondary = 48dp — correct, it's overflow chrome never touched mid-song.
Design call: alias is shown as the row's primary text with the raw pedal name demoted to a caption underneath, rather than showing both at equal weight or hiding the raw name entirely — the raw name is read-only ground truth from the pedal, so it stays visible but subordinate. Presets without an alias just show the raw pedal name as primary text (rows 01–04, 06, 08–19 above).

Tokens in play

  • Colors: status.connected #34D177 filled circle · status.connecting #52B8FF hollow ring · status.disconnected #9AA0A6 hollow ring · status.error #FF5252 filled triangle — exactly D1 §2.3's four states and silhouettes, no deviation.
  • Silhouettes double-encode meaning per D1's explicit requirement: filled circle = "good, live"; hollow ring = "nothing there" (both Connecting and Disconnected share this ring, distinguished only by color+text, per D1's own reasoning that Connecting "is still not yet connected"); filled triangle = "something is wrong." No spinner, no pulse — D1 §5 forbids animating the connecting glyph.

Contrast — verified, not eyeballed

  • status.connected on surface.base: 9.40:1 (D1 §2.4, verified) — pass vs 3:1 graphical minimum.
  • status.disconnected on surface.base: 7.09:1 (D1 §2.4) — pass.
  • status.error on surface.base: 5.87:1 (D1 §2.4) — pass vs 4.5:1 text minimum (banner title is text-sized, held to the stricter bar).
  • Banner titles sit on surface.raised-1, not base — recomputed for this file (not in D1's own table): status.error on raised-1 = 5.28:1 (D1 already lists this exact pair, §2.4) — pass. status.disconnected on raised-1 = 6.38:1 (D1 §2.4) — pass.
Note: the 5-value ConnectionState sealed interface in protocol/ (Idle / Connecting / Hello / GetState / Ready / Error) collapses to these 4 UI states as: Idle → Not Connected, Connecting+Hello+GetState → Connecting…, Ready → Connected, Error(cause) → Error (with cause.message shown, as in the banner above, which uses a realistic TransportFailure message). This mapping is read from protocol/ for accuracy only — not modified.

First-Destructive-Write Warning

Shown once per session, the moment the first parameter edit against a snapshotted preset is committed.

Changes save instantly

Tonex-OTG writes every change straight to the pedal as you make it. There's no undo on the pedal itself.

A snapshot of Set Opener was taken the moment it became active. You can revert to it any time from Settings — until then, experiment freely.

This message appears once per session.

Got it
  • Colors: surface.raised-2 dialog surface (D1 names dialogs as raised-2's usage explicitly), accent.primary filled CTA, on-accent label.
  • Type: type.headline 24sp dialog title, type.body 16sp explanatory copy, type.caption 13sp "appears once" footnote.
  • Single button, no "Cancel" — dismissing is proceeding; this is a heads-up, not a fork. Button sized to touch.target.min 64dp (.btn-tall) even though it's chrome, not performance-critical, because it gates the user's understanding of an irreversible-write mode — cheap to make it impossible to fumble.
  • SnapshotStore.hasWarnedThisSession() / markWarned() in protocol/ already model exactly this "once per session" gate — this screen is that flag's UI.

Design reasoning for "hard to hit by accident"

  • The entry point lives in Settings, not on the parameter-editor screen a musician is actively touching mid-song — physical separation from the high-frequency flow is the first safety layer.
  • The entry-point button is touch.target.secondary 48dp and btn-outline styling (no accent fill), not sized or colored to invite a quick tap — it reads as an available option, not an inviting action.
  • The confirm dialog inverts the usual button hierarchy on purpose: Cancel is the accent-filled, visually primary button; Revert Anyway is the plain outline button. The safe path looks like the default path. This is the actual "hard to hit by accident" mechanism — not size, not color-coding the destructive option red.
  • Copy states the consequence in concrete terms (all 109 parameters, immediate, no undo of the undo) rather than a generic "Are you sure?".
Open question for the lead: D1 has no generic "destructive action" color token — status.error is scoped explicitly to connection state in §2.3's own section title. I deliberately did not reuse status.error for the "Revert Anyway" button, to avoid it being misread as a connection problem. Safety here is carried entirely by placement, copy, and button-hierarchy inversion instead. If a future story wants a red "destructive" affordance elsewhere in the app, D1 will need a new token for it — I did not invent one.

Tonex-OTG ports USB protocol logic from two upstream open-source projects into Kotlin for Android. This screen records where that logic came from and under what licence.

TonexOneController

Repository: https://github.com/Builty/TonexOneController Licence: Apache License 2.0 (SPDX: Apache-2.0) Copyright 2025 Greg Smith

Ported: the Tonex parameter table (parameter IDs, scaling, min/max); preset-details response handling; and state-blob field offsets (input trim, stomp mode, cab bypass, tuning mode/reference, BPM, tempo source, direct monitor, current slot, bypass mode, slot presets).

tonex_controller

Repository: https://github.com/vit3k/tonex_controller Licence: MIT License (SPDX: MIT) Copyright (c) 2024 vit3k

Ported: equivalent HDLC-style byte-stuffing / frame delimiting and CRC-16 checksum logic (reversed polynomial 0x8408), which appears independently in both upstream projects.
