Tokens in play

  • Colors: surface.base, surface.raised-1 (rows, app bar), surface.raised-3 (active row fill — this is exactly D1's documented use for raised-3: "pressed/active fill on a raised-1 element"), accent.primary (selection ring + index badge fill), status.connected (app-bar chip).
  • Type: type.display.preset 57sp/700 for the active preset name — the one non-negotiable tier per D1 §3 — plus type.display.index 45sp for its slot number, type.title 22sp for list rows, type.caption 13sp for the "from pedal:" provenance line and alias sub-line.
  • Spacing: space.3 (16dp) content padding, touch.target.spacing (8dp) gap between rows.

Touch targets

  • Each preset row: touch.target.min = 64dp tall (measured, including the active row) — a preset switch is the single most performance-critical action in the app. Pass.
  • Row-to-row gap: 8dp, matching touch.target.spacing, so a mis-tap at arm's length can't land on the neighboring preset. Pass.
  • Settings gear (top-right): touch.target.secondary = 48dp — correct, it's overflow chrome never touched mid-song.
  • Master Volume dock (bottom, new in this revision): the whole bar is touch.target.min 64dp tall — this is the single most stage-critical control in the app (matching volume between songs), so it gets the largest tier even though it's chrome rather than a preset action. Pass.
Design call: alias is shown as the row's primary text with the raw pedal name demoted to a caption underneath, rather than showing both at equal weight or hiding the raw name entirely — the raw name is read-only ground truth from the pedal, so it stays visible but subordinate. Presets without an alias just show the raw pedal name as primary text (rows 01–04, 06, 08–19 above).
Master Volume, revised this pass: pinned to the bottom of every screen (shown here and on the parameter editor, screen 2) using surface.raised-1 — the exact token D1 assigns to "top app bar, bottom bar" (§2.1) — deliberately not surface.raised-2, the per-preset param-card token, so its global scope reads as chrome, not as "part of this preset." The primary numeral is the pedal's own 0–10 scale (matches what's printed on the hardware screen — no new mental model to learn); the true engineering range (−40..+3 dB, confirmed in ParameterSpec's doc comment) is shown small underneath for anyone cross-referencing firmware docs. Conversion assumed linear (dB = −40 + value/10 × 43) for this mockup only — flagged in mockups.md as unconfirmed against the pedal's actual curve.

Tokens in play

  • Colors: surface.raised-2 (param card — matches D1's "parameter-edit panels" usage exactly), surface.raised-3 (track + value chip fill), accent.primary (slider fill/thumb — D1 §2.2 names this exact usage — also used for the "resolves to" indirection caption, since it's informational/interactive, not a status reading), surface.raised-1 (Master Volume dock — see screen 1's annotation for why this token specifically).
  • Type: type.body-large 18sp for parameter names (D1 names this exact usage too), type.title 22sp bold for the numeric readout, type.caption 13sp for the pedal-abbreviation line under every control.

Touch targets

  • Slider hit band: touch.target.min = 64dp tall, centered on an 8dp visual track — the thumb graphic is small but the invisible tap/drag band around it is full 64dp, satisfying D1 §4.2's "any control used mid-performance" without an oversized visual track dominating the card. Pass.
  • Numeric value chip (tap to open exact-entry, screen 2b): 48dp min — treated as touch.target.secondary since precise numeric entry is a between-songs action, not the mid-song slider drag. Pass.
  • Master Volume dock: 64dp, same reasoning as screen 1.
Banked structure: Reverb Mix and Delay Mix are not single wire parameters. The pedal has one reverb-mix value per reverb model (RVB S1 M … RVB PL M, six total, only one live) and one delay-mix value per delay model (DLY DT X for Digital, DLY TA X for Tape — real abbreviations from the S6 parameter registry). The quick-tier card always shows and edits whichever one is currently live — it does not let you pick a model (that's done in the full editor, screen 2c) and it does not show six sliders. The small "resolves to" line makes that indirection visible rather than silent, specifically so it can't get discovered and bolted on badly during implementation.
Master Volume is still deliberately not a quick-tier card — it's global, not per-preset (ParameterId.kt's ParameterScope.GLOBAL comment), so it would misleadingly imply a per-preset reset if shown here. It now has its own persistent, always-reachable dock instead (bottom of this screen and screen 1) — see that annotation for the design.

Tokens in play

  • Colors: surface.raised-1 (category header), on-surface.tertiary (counts, bank-notes), accent.primary (active model chip fill, "Quick tier"/"Persistent dock" pointer chips), on-surface.disabled (the "Known unknown" / "Inferred" / "S20" tags — deliberately the quietest token in the palette, not status.error, since these mark provenance, not a problem the player needs to react to).
  • Type: type.body-large category names, type.body parameter rows and model chips, type.caption pedal-abbreviation captions and bank-notes.

Touch targets

  • Category header rows, individual parameter rows, model-selector chips: touch.target.secondary = 48dp, not 64dp — D1 §4.2 reserves 64dp for mid-performance controls; both menu-diving and picking a reverb/mod/delay model are between-songs actions. Pass (correctly the smaller tier).

Banked-parameter structure

  • Reverb, Modulation, and Delay each show their 3 always-on controls (a chain-position switch, an enable switch, and the model selector), then a model-selector chip row. Choosing a chip swaps which parameter block renders beneath it; non-active models are not rendered at all — no grayed-out rows.
  • Cabinet gets the same pattern for its VIR mic sub-block: the 9 VIR-specific parameters render only when mode = VIR; Tone Model and Disabled modes have no cabinet-specific parameters of their own in the registry.
  • Category counts reconcile exactly to 109 across 8 preset-scoped groups — Noise Gate 5, Compressor 5, EQ 8, Tone Model/Amp 8, Cabinet 10, Modulation 31, Delay 15, Reverb 27 — plus Global's 7, matching the registry's own "116 parameters (109 + 7)" doc comment. This is a smaller, real set of groups than the previous revision's 11 invented categories — the actual pedal's parameter layout is simpler than the earlier guess.
Human-label layer — the principle: every row above pairs a readable label with the pedal's raw abbreviation in a .pedal-abbr caption underneath, and every label is derived directly from the row's enumName in the registry (e.g. NOISE_GATE_THRESHOLD → "Threshold," trimming the block name since the accordion heading already supplies it) — not invented. Two rows are marked Inferred on screen because their meaning genuinely isn't given by the registry: the *_TS selectors ("Sync Division") are my best guess at what an 18-option selector next to a Sync switch does, not a confirmed label — flagged visibly, not silently presented as fact.
Dropped from the previous revision, not carried forward: "Power Amp," "FX Loop / Routing," and "Expression / Wah" categories, and Cabinet's invented "Low Cut / High Cut / Resonance / Air" core rows — none of these exist in the real registry. Removed rather than kept as illustrative, per instruction: anything not backed by a real row comes out of the rendered screens.

Tokens in play

  • Colors: status.connected #34D177 filled circle · status.connecting #52B8FF hollow ring · status.disconnected #9AA0A6 hollow ring · status.error #FF5252 filled triangle — exactly D1 §2.3's four states and silhouettes, no deviation.
  • Silhouettes double-encode meaning per D1's explicit requirement: filled circle = "good, live"; hollow ring = "nothing there" (both Connecting and Disconnected share this ring, distinguished only by color+text, per D1's own reasoning that Connecting "is still not yet connected"); filled triangle = "something is wrong." No spinner, no pulse — D1 §5 forbids animating the connecting glyph.

Contrast — verified, not eyeballed

  • status.connected on surface.base: 9.40:1 (D1 §2.4, verified) — pass vs 3:1 graphical minimum.
  • status.disconnected on surface.base: 7.09:1 (D1 §2.4) — pass.
  • status.error on surface.base: 5.87:1 (D1 §2.4) — pass vs 4.5:1 text minimum (banner title is text-sized, held to the stricter bar).
  • Banner titles sit on surface.raised-1, not base — recomputed for this file (not in D1's own table): status.error on raised-1 = 5.28:1 (D1 already lists this exact pair, §2.4) — pass. status.disconnected on raised-1 = 6.38:1 (D1 §2.4) — pass.
Note: the 5-value ConnectionState sealed interface in protocol/ (Idle / Connecting / Hello / GetState / Ready / Error) collapses to these 4 UI states as: Idle → Not Connected, Connecting+Hello+GetState → Connecting…, Ready → Connected, Error(cause) → Error (with cause.message shown, as in the banner above, which uses a realistic TransportFailure message). This mapping is read from protocol/ for accuracy only — not modified.

First-Destructive-Write Warning

Shown once per session, the moment the first parameter edit against a snapshotted preset is committed.

Changes save instantly

Tonex-OTG writes every change straight to the pedal as you make it. There's no undo on the pedal itself.

A snapshot of Set Opener was taken the moment it became active. You can revert to it any time from Settings — until then, experiment freely.

This message appears once per session.

Got it
  • Colors: surface.raised-2 dialog surface (D1 names dialogs as raised-2's usage explicitly), accent.primary filled CTA, on-accent label.
  • Type: type.headline 24sp dialog title, type.body 16sp explanatory copy, type.caption 13sp "appears once" footnote.
  • Single button, no "Cancel" — dismissing is proceeding; this is a heads-up, not a fork. Button sized to touch.target.min 64dp (.btn-tall) even though it's chrome, not performance-critical, because it gates the user's understanding of an irreversible-write mode — cheap to make it impossible to fumble.
  • SnapshotStore.hasWarnedThisSession() / markWarned() in protocol/ already model exactly this "once per session" gate — this screen is that flag's UI.

Design reasoning for "hard to hit by accident"

  • The entry point lives in Settings, not on the parameter-editor screen a musician is actively touching mid-song — physical separation from the high-frequency flow is the first safety layer.
  • The entry-point button is touch.target.secondary 48dp and btn-outline styling (no accent fill), not sized or colored to invite a quick tap — it reads as an available option, not an inviting action.
  • The confirm dialog inverts the usual button hierarchy on purpose: Cancel is the accent-filled, visually primary button; Revert Anyway is the plain outline button. The safe path looks like the default path. This is the actual "hard to hit by accident" mechanism — not size, not color-coding the destructive option red.
  • Copy states the consequence in concrete terms (all 109 parameters, immediate, no undo of the undo) rather than a generic "Are you sure?".
Open question for the lead: D1 has no generic "destructive action" color token — status.error is scoped explicitly to connection state in §2.3's own section title. I deliberately did not reuse status.error for the "Revert Anyway" button, to avoid it being misread as a connection problem. Safety here is carried entirely by placement, copy, and button-hierarchy inversion instead. If a future story wants a red "destructive" affordance elsewhere in the app, D1 will need a new token for it — I did not invent one.

Tonex-OTG ports USB protocol logic from two upstream open-source projects into Kotlin for Android. This screen records where that logic came from and under what licence.

TonexOneController

Repository: https://github.com/Builty/TonexOneController Licence: Apache License 2.0 (SPDX: Apache-2.0) Copyright 2025 Greg Smith

Ported: the Tonex parameter table (parameter IDs, scaling, min/max); preset-details response handling; and state-blob field offsets (input trim, stomp mode, cab bypass, tuning mode/reference, BPM, tempo source, direct monitor, current slot, bypass mode, slot presets).

tonex_controller

Repository: https://github.com/vit3k/tonex_controller Licence: MIT License (SPDX: MIT) Copyright (c) 2024 vit3k

Ported: equivalent HDLC-style byte-stuffing / frame delimiting and CRC-16 checksum logic (reversed polynomial 0x8408), which appears independently in both upstream projects.
